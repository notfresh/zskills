# se-first —— 启用软件工程思维

> 原则：先想清楚再下笔。写代码前 5 分钟省的下游 5 小时。

## 触发边界（必须满足其一才走）

1. **≥2 个文件**的非琐碎改动（修复 typo / 改字符串字面量不算）
2. **新公共 API**（新函数被其他模块 import、新 CLI 入口、新 HTTP route）
3. **重构 / 抽公共 / 改既有架构**
4. **引入新依赖**（requirements.txt / package.json / go.mod 新增项）

单文件小改、单点 bugfix、文案/注释修改 —— 不触发，直接动手。

> **执行纪律（2026-10-02 教训）**：触发后 **必须 `skill_view(name='se-first')` 加载本 skill 再开始自审**，
> 不可凭印象/记忆写"自审报告"。用户的反应就是判官 —— "等一下你改的改动符合软件工程思维吗？
> 加载SEFIRST技能先审视一下啊" —— 意味着口头自审不算数,必须真的把 skill 内容读进来再答三问。
>
> 常见漏点（自己跑易忘）:
> - 漏 `新增依赖` 行 —— 随手 mock 一个 Android framework class 算不算新依赖？
> - 漏 `回滚成本` —— "单 commit revert" 必须真成立(没改 Schema/协议/迁移)
> - 把"需要一个接口/依赖"当 Q3 反对理由 —— 必须量化新增表面积、测试边界和实际收益
> - 改动清单漏"派生改动"项 —— 改 A → 必然改 B 的要标出来,别等用户问"那 B 呢"

## 三原则（不可妥协）

1. **高内聚、低耦合、单一职责** —— 一个模块只做一件事，模块间少耦合。
2. **存量少改** —— 既有代码默认不动；新代码落实新原则，老代码维持原样。
3. **简单优先** —— 复杂 vs 简单，选简单的（易理解、易维护、易回滚）。

## 自审三问（动手前必答，不答不许写）

| # | 问 | 红线示例 |
|---|---|---|
| **Q1 单一来源** | 3 处近复制代码 → 能不能参数化成一个？ | 3 个 `if host == "x" / "y" / "z"` 分支 → 抽成 map / 策略表 |
| **Q2 命名单元** | 分支 / 嵌套逻辑能不能抽成有名字的函数 / 策略对象？ | 5 层 `if-else` 套娃 → 抽成 `class Strategy` 或 `def decide(x) -> Action` |
| **Q3 表面积 ∝ 价值** | 加的字段 / 维度 / 持久化 / wrapper 真的有人用吗？能不能删？ | 加了 `host` 维度但没清除入口 → 单向门（只进不出），坚决不建 |

每一问如果答不出"删它 / 合它"，就该删 / 合。

## 动词字面义（来自 2026-10-01 安卓教训）

用户说"加按钮"= **一个按钮**，不是：
- 顺手加 wrapper / 抽象层
- 顺手加持久化 / 配置项
- 顺手加全局状态 / 单例
- 顺手加新维度（host / user_id / scope）

**自检**：改动清单每一项都能在用户原话里找到出处？做不到 → 回退 / 先问。

## 报告模板（动手前 30 秒交）

```
改动清单（每项必须有原话出处）：
1. <改什么 / 哪个文件>
2. ...

SE 自审：
- Q1 单一来源：[通过 / N/A，理由]
- Q2 命名单元：[通过 / N/A，理由]
- Q3 表面积 ∝ 价值：[通过 / N/A，理由]

存量影响：[0 处 / 列文件:行号]
新依赖：[0 / 列出]
回滚成本：[单 commit revert / 需手工回滚 N 处]
```

老规矩：**先报告，等用户点头，再下笔**。出现"动手 / 改吧 / 修复"等明确指令时，可省略报告直接执行，但仍要在脑内跑完三问。

### 否定用户拍板的方案时：必须给出更轻的替代

如果用户拍板 A/B/C 而你倾向另一方案,**说"不"之前必须**:
1. 量化 A 的真实代价(行数 / 依赖 / 测的是哪层)
2. 给出**至少一个更轻的具体替代方案**(不是 "我觉得不行")
3. 让用户二次拍板 —— 不替用户做决定

反例:用户说"用 B 吧",回"B 不行" —— 用户被堵了,没选项。
正例:回"B 会增加一层依赖，但只覆盖接口契约，推荐 D —— 缩窄接口边界，测试直接覆盖真正需要验证的行为，零新依赖"。

**判别**:能否让用户拿更轻方案后立刻拍板? 拿不出更轻方案 = 自己想得不够,继续想。

## 反例速查

- 新增维度却没有清除、迁移或回滚路径：删掉，避免单向门。
- 重复的条件分支没有抽成表、策略或命名函数：先收敛再扩展。
- 既有逻辑能跑就不动：优先控制存量影响。
- 触发技能后凭记忆自审：先加载当前技能，再回答三问。
- 改动后才发现测试原本就失败：先确认基线，区分存量失败与引入的失败。
- 大块修改导致缩进或结构不确定：停止叠加 patch，改用更小的局部修改或整体重写，并立即验证。
- 回调捕获了会变化的局部变量：先固定最终值，再交给回调。
- 已有接口能完成通信：不要为了换接口而增加状态、注册表或 token。
- 修改签名却漏列调用方：把所有派生改动写入“存量影响”。
- 用户已经明确同意后不要重复提交自审报告；确认一次即可。
- 需求反转时先确认已有改动，再只问一个回滚或叠加问题。
- 指代可能对应多个对象：不要猜，先问一个最小澄清问题。
